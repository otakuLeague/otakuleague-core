# API with the database (moved from CLAUDE.md)

The API loads the repo-root `.env` (real env vars win) and refuses to boot, exit code 1, with one message listing every missing or invalid variable (`NODE_ENV`, `PORT`, `DATABASE_URL`).
1. `cp .env.example .env` (an older `.env` needs `NODE_ENV=development` added), then `pnpm db:up`.
2. `pnpm db:migrate` (runs `prisma migrate deploy` in the API): apply migrations to the dev DB (`prisma migrate status` to check).
3. `pnpm dev`, or `pnpm build && pnpm --filter @otakuleague/api start`.
4. `curl localhost:3001/health`: 200 `{"status":"ok",...}`, or 503 while Postgres is down (the API keeps running and recovers by itself). Swagger UI at `/docs`, JSON at `/docs-json`, both off when `NODE_ENV=production`.
- Prisma CLI: run it inside apps/api (`pnpm --filter @otakuleague/api exec prisma ...`); `pnpm install` regenerates the client into `apps/api/src/generated` (gitignored). After a schema change: `prisma migrate dev --name <change>`, then `prisma generate`.
- Migrations: `migrate dev` only against the dev DB; `migrate deploy` for production; the integration suite migrates the test DB itself. Never edit an applied migration; add a new one.
- Additive first (OTA-183, see `docs/deploy.md` where migrations already follow this): web and API deploy separately. Expand the API (new field, new route), migrate the web app, contract in a later PR. Never remove or rename a response field in the same PR as the web change that stops using it.
- Unit tests point `DATABASE_URL` at a closed port; anything that queries Postgres is a `*.integration.spec.ts`. Copy `apps/api/src/testing/example.integration.spec.ts` (inject `Clock` and `Random`, never `new Date()` or `randomUUID()`). If Postgres is down the integration suite stops with "Run `pnpm db:up`"; "Another integration run is using ..." means two runs overlap.
- Internal API key (ADR 0019, OTA-182): `InternalKeyGuard` (`src/common/internal-key.guard.ts`) is the global `APP_GUARD`. With `INTERNAL_API_KEY` unset every route is open (one start-up warning in production, logged and sent to Sentry via `captureStartupWarning`; boot refused only when `INTERNAL_API_KEY_REQUIRED=true`, any `NODE_ENV`, the preview key does not count); set, every route needs it or `INTERNAL_API_KEY_PREVIOUS` in `X-Internal-Api-Key`, else 403 `INTERNAL_KEY_REQUIRED` (one answer for missing, wrong, repeated, too short or over-long). `INTERNAL_API_KEY_PREVIEW` (Vercel previews, refused at boot if equal to either key, inert while the key is unset) is checked after them with a second `isAcceptedKey` call. Keys: 43-128 chars of `[A-Za-z0-9_-]` (`openssl rand -hex 32`), empty means unset. Compare a presented key only through `isAcceptedKey` (SHA-256 both sides, then `timingSafeEqual`), never `===` (the boot check that the preview key differs compares env values only). Only `GET /health` carries `@PublicRoute()` (method-only); `internal-key.integration.spec.ts` lists the public handlers and fails on a new one. Unit and integration setups pin all four variables to empty, so a local `.env` key never leaks into tests. Tests switch the check with `overrides: [{ provide: InternalKeySettings, useValue: { get: () => check } }]`, or set `process.env.INTERNAL_API_KEY` in `vi.hoisted` to test the real wiring (`internal-key.env.integration.spec.ts`); obvious fake keys only, never a real one. Never log the key or the header. The guard also records an `ApiCaller` per request (`src/common/api-caller.ts`, a WeakMap no header or body can write): `open` while no key is configured (`X-Client-Ip` never read), `web` with a visitor key once the key matched (`visitorKeyFromClientIp`: IPv4, mapped IPv4 as IPv4, IPv6 cut to /64, anything else `unknown`), `preview` for the preview key (`X-Client-Ip` never read, one shared bucket `preview`); a credential route (OTA-139) must allowlist `web` only; a refused request or a `@PublicRoute()` handler records nothing, and `@Caller()` then throws (500), never defaults to `open`. A handler that can start work per visitor takes `@Caller() caller: ApiCaller` and passes it down explicitly. `ApiException` takes `{ retryAfterSeconds }`; the filter sends `Retry-After` only for a positive integer.
