# API with the database (moved from CLAUDE.md)

The API loads the repo-root `.env` (real env vars win) and refuses to boot, exit code 1, with one message listing every missing or invalid variable (`NODE_ENV`, `PORT`, `DATABASE_URL`, and `AUTH_HMAC_KEY` when `NODE_ENV=production`).
1. `cp .env.example .env` (an older `.env` needs `NODE_ENV=development` added), then `pnpm db:up`.
2. `pnpm db:migrate` (runs `prisma migrate deploy` in the API): apply migrations to the dev DB (`prisma migrate status` to check).
3. `pnpm dev`, or `pnpm build && pnpm --filter @otakuleague/api start`.
4. `curl localhost:3001/health`: 200 `{"status":"ok",...}`, or 503 while Postgres is down or its session time zone is not UTC (the API keeps running and recovers by itself once Postgres is back; a non-UTC zone does not recover by itself). Swagger UI at `/docs`, JSON at `/docs-json`, both off when `NODE_ENV=production`.
- Prisma CLI: run it inside apps/api (`pnpm --filter @otakuleague/api exec prisma ...`); `pnpm install` regenerates the client into `apps/api/src/generated` (gitignored). After a schema change: `prisma migrate dev --name <change>`, then `prisma generate`.
- Migrations: `migrate dev` only against the dev DB; `migrate deploy` for production; the integration suite migrates the test DB itself. Never edit an applied migration; add a new one.
- Additive first (OTA-183, see `docs/deploy.md` where migrations already follow this): web and API deploy separately. Expand the API (new field, new route), migrate the web app, contract in a later PR. Never remove or rename a response field in the same PR as the web change that stops using it.
- Unit tests point `DATABASE_URL` at a closed port; anything that queries Postgres is a `*.integration.spec.ts`. Copy `apps/api/src/testing/example.integration.spec.ts` (inject `Clock` and `Random`, never `new Date()` or `randomUUID()`). If Postgres is down the integration suite stops with "Run `pnpm db:up`"; "Another integration run is using ..." means two runs overlap.
- Session time zone (OTA-200): every app and test pool (`PrismaService`, `connectTestDatabase`) is pinned to UTC by `databasePoolConfig` (`src/prisma/database-pool.ts`, `options: '-c timezone=UTC'`), because `@prisma/adapter-pg` drops the offset on `timestamptz` reads and writes; build any new client with it. Never put `options=` in `DATABASE_URL`: pg lets the URL win, so boot validation lists it as invalid and the helper refuses it too. Not pinned: the maintenance connection (`connectMaintenance`), `prisma migrate` and psql, which run in the database's own zone, so migration SQL writes every timestamp literal with an explicit offset (`'2026-01-01 00:00:00+00'`), never a bare one. `GET /health` reads `current_setting('TimeZone')` and answers 503 (one warning, zone capped at 64 chars) unless it is exactly `UTC` (OTA-201): a pooler such as PgBouncer can drop the startup `options`, and the pin would then fail silently.
- Internal API key (ADR 0019, OTA-182): `InternalKeyGuard` (`src/common/internal-key.guard.ts`) is the global `APP_GUARD`. With `INTERNAL_API_KEY` unset every route is open (one start-up warning in production, logged, and sent to Sentry at error level via `captureStartupError`; boot refused only when `INTERNAL_API_KEY_REQUIRED=true`, any `NODE_ENV`, the preview key does not count); set, every route needs it or `INTERNAL_API_KEY_PREVIOUS` in `X-Internal-Api-Key`, else 403 `INTERNAL_KEY_REQUIRED` (one answer for missing, wrong, repeated, too short or over-long). `INTERNAL_API_KEY_PREVIEW` (Vercel previews, refused at boot if equal to either key, inert while the key is unset) is checked after them with a second `isAcceptedKey` call. Keys: 43-128 chars of `[A-Za-z0-9_-]` (`openssl rand -hex 32`), empty means unset. Compare a presented key only through `isAcceptedKey` (SHA-256 both sides, then `timingSafeEqual`), never `===` (the boot check that the preview key differs compares env values only). Only `GET /health` carries `@PublicRoute()` (method-only); `internal-key.integration.spec.ts` lists the public handlers and fails on a new one. Unit and integration setups pin all four variables to empty, so a local `.env` key never leaks into tests. Tests switch the check with `overrides: [{ provide: InternalKeySettings, useValue: { get: () => check } }]`, or set `process.env.INTERNAL_API_KEY` in `vi.hoisted` to test the real wiring (`internal-key.env.integration.spec.ts`); obvious fake keys only, never a real one. Never log the key or the header. The guard also records an `ApiCaller` per request (`src/common/api-caller.ts`, a WeakMap no header or body can write): `open` while no key is configured (`X-Client-Ip` never read), `web` with a visitor key once the key matched (`visitorKeyFromClientIp`: IPv4, mapped IPv4 as IPv4, IPv6 cut to /64, anything else `unknown`), `preview` for the preview key on GET and HEAD only, any other method 403 (`X-Client-Ip` never read, one shared bucket `preview`); a credential route (OTA-139) must allowlist `web` only; a refused request or a `@PublicRoute()` handler records nothing, and `@Caller()` then throws (500), never defaults to `open`. A handler that can start work per visitor takes `@Caller() caller: ApiCaller` and passes it down explicitly. `ApiException` takes `{ retryAfterSeconds }`; the filter sends `Retry-After` only for a positive integer.
- Sessions (ADR 0015, OTA-139 slice 1a, `src/auth/`): `GET /me` sits behind `@UseGuards(SessionGuard)`, which runs after `InternalKeyGuard`, accepts only a `web` caller, without a lookup otherwise: `open` gets 403 `INTERNAL_KEY_REQUIRED` (a key missing on the API must never look like a sign-out, ADR 0017; locally set `INTERNAL_API_KEY` to try it), `preview` 401; it reads `Authorization: Bearer <43 base64url chars>` strictly (`sessionTokenFromHeader`; anything else 401 with no query). Every session refusal is the same 401 `UNAUTHORIZED` (`SESSION_REQUIRED_MESSAGE`); database errors are never caught, so an outage is a 503, never a sign-out. Tokens are stored only as `hashSessionToken` (SHA-256) in `auth_session.token_hash`; validity is the pure `sessionValidity` (`session-rules.ts`: epoch match, 30 days idle renewed under 15 days left, 180-day hard stop, NaN means expired). `SessionService.resolve` does one joined lookup (verified users only) and at most one compare-and-set `updateMany` (same `expiresAt` and user epoch as read), and logs nothing. CHECKs in SQL only: lower-case `email`, 32-byte `token_hash`. Handlers read the member with `@CurrentSession()` (WeakMap written only by the guard, throws 500 without it), never from a body; answers carrying a member send `Cache-Control: no-store`. Tests seed `User` + `Session` with an obvious fake token (`me.integration.spec.ts`).
- Passwords (ADR 0015, OTA-139 slice 1b): only through `PasswordHasher` (`src/auth/password-hasher.ts`, the one export of `AuthModule`). Every route's per-IP rate limit runs before any `PasswordHasher` call (ADR 0015, "Why Postgres for rate limits"). `hash` NFC-normalises, refuses more than `MAX_PASSWORD_BYTES` (1024 UTF-8 bytes after NFC) with 400 `BAD_REQUEST`, salts with `Random.bytes(16)` and returns a PHC string (`password-phc.ts`: `ARGON2_PARAMS` m=19456 t=2 p=1, 32-byte tag); `verify(password, phc | null)` answers `'match' | 'mismatch'`, compares with `timingSafeEqual`, uses the stored parameters, and runs one dummy verification for a null or unreadable hash or an over-long password (`parsePhc` is strict and bounded: at most 64 MiB, 10 passes, p=1 only since p > 1 starts OpenSSL threads outside the libuv pool), so a missing account costs the same; `needsRehash` is true when the hash is unreadable or any parameter is below `ARGON2_PARAMS` (never just different: a rollback must not downgrade hashes). `NodeArgon2id` is the only caller of `crypto.argon2` (Node >= 24.7; on older Node it fails per call, never at boot); unit tests replace `Argon2id` with a fast fake, `password-hasher.integration.spec.ts` pins a libargon2 vector. `HashSlots`: 2 hashes run, 8 wait in FIFO order, the next gets 429 `AUTH_BUSY` with `Retry-After: 1`, without running, and one warning a minute (429, not 503: the filter logs every 5xx with a stack, ADR 0019). Optional work uses `tryHash` (`HashSlots.tryRun`): it runs only in a slot free right now with nobody waiting, else `skipped`, never queued and never `AUTH_BUSY`. Never log a password, a hash or a salt.
- Auth rate limits (ADR 0015, OTA-139 slice 1c-i): in Postgres, not `VisitorBuckets` (the one exception: auth counters must survive a deploy and a second instance). `AuthRateLimiter.check(hits)` (`src/auth/auth-rate-limiter.ts`) runs one autocommit `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` per key in order and stops at the first refusal (later keys are not counted; the per-IP key goes first); database errors propagate (503), never an uncounted pass. `check` takes only `RateLimitHits` built by a route's builder (`signInHits`: ip, then (identifier, IP), then identifier, each with its `SIGN_IN_LIMITS` rule); keys come from `rateLimitKey` (`auth-rate-limit-rules.ts`: HMAC-SHA256 with `AUTH_HMAC_KEY` over a JSON array, parts typed as `ClientIpKey` and `NormalisedIdentifier`), never a raw IP or identifier. `clientIpKey` returns null for the shared `unknown` and `preview` buckets: the route refuses that request, never counts it in a shared bucket. Accepted trade-offs: fixed windows anchored at a key's first attempt allow a burst of 2 x limit - 1 across a boundary; the identifier ceiling is per spelling (email and username apart, up to 2x per account), because one counter per account would let a caller link a username to an email; `SIGN_IN_LIMITS` is pinned to the ADR by a test; `decide` gives `retryAfterSeconds` (rounded up, 1 to the window). Times go to SQL with an explicit UTC offset (`toISOString()::timestamptz`) and come back as epoch ms: the pg adapter drops a timestamptz offset on read. `AUTH_HMAC_KEY`: same shape as `INTERNAL_API_KEY`, required in production (boot refused), refused when equal to any `INTERNAL_API_KEY*`, a random 32-byte key per process elsewhere; read only through `AuthSecrets` (a `KeyObject`, prints no key material; tests override the provider; one start-up warning when the key was drawn); unit and integration setups pin it empty. Credentials go through `credential-rules.ts` (`normalisePassword` NFC, `passwordLength` in code points, `normaliseIdentifier` trim + lower-case + NFC). Rows are deleted by the auth cleanup (slice 1d) once their window started `RATE_LIMIT_LONGEST_WINDOW_MS` (24 h) ago; `AuthRateLimiter` throws before counting under a rule with a longer window.
- Credential routes (ADR 0015, OTA-139 slice 1c-ii, `src/auth/auth.controller.ts`): `POST /auth/sign-in` sits behind `@UseGuards(CredentialGuard)` (`credential.guard.ts`), which runs after `InternalKeyGuard` and before validation: `open` and `preview` callers get 403 `INTERNAL_KEY_REQUIRED`, a `web` caller whose `clientIpKey` is null (no or invalid `X-Client-Ip`, the shared `unknown` bucket) 400 `BAD_REQUEST` (`CLIENT_IP_REQUIRED_MESSAGE`), so neither costs a counter or a hash; handlers read the IP with `@ClientIp()` (WeakMap written only by the guard, 500 without it), never from a header or body. `SignInDto` checks upper bounds and non-empty only (identifier not blank, at most `IDENTIFIER_MAX` UTF-16 units and no U+0000; password at most `PASSWORD_RAW_MAX` UTF-16 units before NFC, then at most `PASSWORD_MAX` code points after NFC, message never echoes the value). NFC on long runs of combining marks is slow and runs before the limiter, so every raw string gets a length cap before any normalisation (`passwordBytes` too: `4 * MAX_PASSWORD_BYTES` units); minimum and composition rules belong to sign-up. `SignInService.signIn` normalises the identifier, calls `AuthRateLimiter.check(signInHits(...))` before the lookup and any hash, looks the user up by `email` or `usernameKey` (`identifierKind`), runs `PasswordHasher.verify` exactly once (the dummy hash for an unknown or unverified account), and on a match `SessionService.create` (32 random bytes, base64url, SHA-256 stored, epoch from that same lookup, expires now + 30 days). Outcomes: 200 `{ sessionToken, expiresAt }` with `Cache-Control: no-store`; one 401 `INVALID_CREDENTIALS` (`INVALID_CREDENTIALS_MESSAGE`) for unknown, unverified and wrong password; 429 `TOO_MANY_REQUESTS` with `Retry-After`; `AUTH_BUSY` and database errors propagate. No counter reset on success, no logging. On `signed_in` only, `PasswordRehasher.schedule` (slice 1c-iii, not awaited, never rejects, one in flight per user, settled in `onModuleDestroy`) rehashes when `needsRehash`: `tryHash` (skipped silently when no slot is free) then a compare-and-set `updateMany` on `{ id, passwordHash: <hash read by the lookup> }` (a password changed in between wins), only `passwordHash` changes (never the epoch); a database error becomes one warning with the user id only (never the error text, which can quote hashes). Tests wait with `settle()`. `POST /auth/sign-out` (`SessionGuard`) deletes the `@CurrentSession()` row only (204; a replay is 401; other sessions stay). Spec: `sign-in.integration.spec.ts` (counting fake `Argon2id`).
- Auth cleanup (ADR 0015, OTA-139 slice 1d): `AuthCleanupScheduler` (`src/auth/auth-cleanup.scheduler.ts`, like `AnimePurgeScheduler`: a minute after boot, then every 24 h, timers unref'd, a running pass joined instead of doubled; on shutdown it skips its remaining steps and is awaited) runs the five `AuthCleanupService` steps in order, each one `deleteMany` with `now` from `Clock` (never SQL `now()`), deleting exactly what the reading rule already treats as ended (`<= now`): rate-limit counters whose window started `RATE_LIMIT_LONGEST_WINDOW_MS` ago; sessions at `expiresAt` or `createdAt + SESSION_MAX_AGE_MS`; tokens at `expiresAt`, used or not; username holds at `expiresAt`; unverified users at their `app_user.pending_expires_at` (their sessions and tokens cascade; null, the state of every user before slice 1e, is never deleted). Slice 1e sets that deadline to now + `PENDING_SIGN_UP_TTL_MS` (`sign-up-rules.ts`, 24 h) in the same UPDATE that re-arms an account on submit and resend, and clears it on verification: Postgres re-checks the target row's columns after waiting on its lock, so a racing re-submit or verification keeps the account. A failing step is one warning and one Sentry warning (`AuthCleanupAlerts`, `captureBackgroundStepFailure`) holding its label and a safe error kind only (a Prisma `P` code or an error class name, never the text); the others still run, then one log line with the five counts; no key, id or hash is ever logged. Tables `auth_token` (`token_hash` PK, `purpose`, `binding_hash`, `used_at`) and `auth_username_hold` (`username_key` PK) exist for slice 1e, and their data, like `auth_rate_limit`'s, is left out of the nightly backup; CHECKs in SQL only: 32-byte `token_hash` and `binding_hash`, a binding on `EMAIL_VERIFICATION` tokens only. Spec: `auth-cleanup.integration.spec.ts` (boundary rows at the cutoff and 1 ms inside).
- Sign-up (ADR 0020, OTA-139 slice 1e-i): `POST /auth/sign-up` (`CredentialGuard`, `SignUpDto`: username `USERNAME_PATTERN` 3-20 `[A-Za-z0-9_]`, email at most 254 raw then a lower-case ASCII shape on `normaliseIdentifier` output, password `PasswordMaxLength` plus 8 code points with a digit or symbol; `sign-up-rules.ts`). `SignUpService.signUp` in this order, never reordered: `EmailSender.canSend()` false is 403 `SIGN_UP_CLOSED` before any counter or write (not a 5xx, which the filter logs with a stack); `perIpHits('sign-up')` (`PER_IP_LIMITS`, 5 per IP per hour); the "taken" read (live hold, or a user row of that key that is not stale) is 409 `USERNAME_TAKEN` with no hash; one `PasswordHasher.hash` outside any transaction; token and `bindingToken` (32 bytes, base64url) drawn in every branch; one transaction of five raw statements in lock order hold, `app_user`, `auth_token` (claim the hold with `ON CONFLICT ... WHERE expires_at <= now`, delete the stale row of that username with the cleanup's predicate, check, upsert by email re-arming `pending_expires_at` only for an unverified row with a deadline, replace the `EMAIL_VERIFICATION` token storing `hashAuthToken` of token and binding), READ COMMITTED set explicitly; a 409 inside it throws to roll back, and a unique violation on `username_key` (`isUsernameKeyConflict`) is 409 too, never a 500. 202 `{ bindingToken }` with `no-store` for a new, pending and registered email alike; a registered row is never changed and its owner gets `sign_up_notice`. Mail goes after the answer through `dispatch` (started by `setImmediate`, never awaited, never rejects, settled in `onModuleDestroy`; a failure is one warning naming the kind and user id only). `EmailSender` (`email-sender.ts`): `emailSenderFor(NODE_ENV)` gives `ConsoleEmailSender` (one JSON line straight to stdout, token included, local only) for development and test, `ClosedEmailSender` for anything else, so production is closed until a real adapter exists. Times go to SQL as ISO `::timestamptz` and none is read back. Spec: `sign-up.integration.spec.ts` (recording sender, counting or gated fake `Argon2id`).
- Email confirmation (ADR 0020 Addendum 1e-ii, OTA-139 slice 1e-ii-a): `POST /auth/email-verification/confirm` (`EmailVerificationController`, `CredentialGuard`, `no-store`), body `EmailVerificationConfirmDto` `{ token, bindingToken?, password? }` (token and binding at most 128 characters, no pattern, so a malformed token is 400 `AUTH_TOKEN_INVALID` from the lookup; password `PasswordMaxLength`; optional means absent, `null` is `VALIDATION_FAILED`). `EmailVerificationService.confirm` in this order, never reordered: `perIpHits('email-verification-confirm')` (10 per IP per 15 min); one read by `hashAuthToken(token)` joined to the user, liveness and "verified" computed in SQL; not found 400, verified user 200 `already_verified` (never a session), used or expired 400; `bindingMatches` (SHA-256, `timingSafeEqual`) verifies and creates a session after commit; otherwise the pre-hijack gate: no password is 200 `confirmation_required` (nothing consumed), a password first counts `confirmPasswordHits` (the account's email, 10 per hour from any IP, 429 with no hash), then exactly one `PasswordHasher.verify` outside any transaction, wrong is 401 `INVALID_CREDENTIALS` (nothing consumed), right verifies with `session: null`. The transaction (READ COMMITTED, user then token, the cleanup's order) locks the user `FOR UPDATE` (verified after the wait: `already_verified`), consumes the token only if still live, this user's and (binding path) still bound to that binding, then verifies only if still unverified and (password path) still holding the hash the password matched; either update finding nothing rolls back to 400. No dummy hash; logs nothing; `AUTH_BUSY` and database errors propagate. Spec: `email-verification.integration.spec.ts` (H1, M2 and C1 attack cases, five parallel confirms give one session).
- Keyed rate limits (ADR 0019): `VisitorBuckets` (`src/common/visitor-buckets.ts`, `{ burst, refillMs, maxEntries }` plus `Clock`) is the one per-visitor limiter, used by `ImportLimits`, `ListFetchLimits` and `SearchLimits`; a new per-visitor limit reuses it, never a second bucket implementation or a throttler package. Every owner of `VisitorBuckets` is swept by `VisitorSweepScheduler` (OTA-197). Key it with `visitorKeyOf(caller)`; `take` returns `retryAfterSeconds` for `ApiException`.
