# OTA-139: email link handler (slice 1f-vi-a)

- Slices so far: #150 shared password rule, #151 v3b-a, #152 v3b-b, this PR 1f-vi-a (`feat/OTA-139-verify-link-1f-vi`): ADR 0015 "Addendum (1f-vi)", the GET handler with its pure core, cookies and gates. Web plus one shared constant: no API change, variable, dependency or error code.
- Shared types: `EMAIL_VERIFICATION_LINK` (`path` `/auth/verify`, `tokenParam` `token`); its test checks the redaction masks `token=` in text. `app/route-handlers.test.ts` holds `app/auth/verify/route.ts` to it.
- Cookies (`auth-cookies.ts`, through `authCookie`): `verifyCookie` (`ol_verify`, 600 s) and `clearedSignUpCookie` (`Max-Age=0`, `Secure` on https). Privacy table row renamed to `__Host-ol_verify` (`lastUpdated` unchanged: same cookie, its real name).
- Pure core `src/auth/email-link.ts`: `EMAIL_LINK_LANDINGS` (six relative constants) and `EmailLinkLanding`; `emailLinkTokenFrom` (exactly one `token`, 43 base64url, else nothing); `wellFormedAuthToken` (the binding's check); `VerifyLinkOutcome` and `verifyLinkOutcomeFrom` (by `outcome` and code only: `AUTH_TOKEN_INVALID` is `expired`, any other failure or refusal `try_again`, `verified` with `session: null` is `confirmed`); `landingOf`.
- `src/auth/see-other.ts`: `seeOther(landing)`, bodiless 303 with `Location`, `Cache-Control: no-store` and the no-Referer policy; the referrer guard names it as its one exception and checks the literal appears exactly once.
- Handler `src/auth/verify-email-link.ts` + `app/auth/verify/route.ts` (GET only), in the addendum's order; `'email-confirm'` joins `AuthCallRoute` and `ClientIpRoute`.
- Gates: `no-restricted-syntax` bans `NextResponse.redirect`/`Response.redirect` (dot, string key, namespace, `globalThis`, destructured) except `src/anime/slug-proxy.ts`; `auth-cookie-importers.test.ts` pins the files naming each cookie helper; `route-handlers.test.ts` pins `hikari` POST and `auth/verify` GET.
- Tests: core table (every row of the addendum, 11 malformed-token cases), `seeOther` on each landing, handler (0 calls and 0 cookie reads on a preview or a bad token, binding only when well-formed and under the configured name, a planted plain `ol_signup` ignored, revoke-then-set-then-clear order, `ol_verify` only on `confirmation_required`, no cookie on replay/`already_verified`/`session: null`/400/429/5xx/outage/refusal, reports only for faults and `client_ip_unknown`, a throw → `try-again` + `configuration`, Next's signal rethrown, the token in no console line, report or scrubbed event), lint rows, scans. Mutation-checked: removing `unstable_rethrow`, `deleteSession`, the binding check, the `ol_signup` clear, or writing `ol_verify` on every outcome each fails a test.
- Decisions: the handler pin lives next to the route (`app/route-handlers.test.ts`) and imports each pinned file with a literal `import()` (lint allows literals only); the scan counts comments too, so a comment naming a helper is a use. The redirect gate catches `globalThis.Response.redirect` and destructuring, beyond the addendum's letter. Read in Next 16.4.6 (`app-route/module.js`): a sync `request.url` in a prerender throws `NEXT_PRERENDER_INTERRUPTED`, which `unstable_rethrow` passes, and `cookies().set()` is merged into a returned `Response`; ADR "Not verified" amended.
- Open Minors: a throw after the session cookie is set (only `jar.set` itself could) would land on `try-again` with the cookie kept; a prefetch or HEAD spends the token (ADR "Too simple?"); `try-again` shows no wait time for a 429; aliased `Response`/`NextResponse` and a hand-written `Location` header are lint blind spots.
- Not verified by running: `next build` with this GET handler under `cacheComponents`, the 303 and its cookies on `next start` and on Vercel's edge, a click from webmail and from a mail app sending the `SameSite=Lax` binding, what Vercel's request log keeps of the query.
