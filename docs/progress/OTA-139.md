# OTA-139: accounts, slice 1d (auth cleanup timer)

- New tables (migration `20261117120000_auth_token_username_hold`, additive): `auth_token` (`token_hash` 32-byte PK, `purpose` enum `auth_token_purpose`, `user_id` FK ON DELETE CASCADE, `binding_hash`, `created_at`, `expires_at`, `used_at`) and `auth_username_hold` (`username_key` PK, `expires_at`). SQL-only CHECKs: 32-byte `token_hash` and `binding_hash`, a binding on `EMAIL_VERIFICATION` only. Nothing writes them yet: slice 1e does.
- `AuthCleanupService` (five `deleteMany`, `now` from `Clock`, each at the cutoff its rule already treats as ended) and `AuthCleanupScheduler` (a minute after boot, then every 24 h; a failing step warns with its label only and the others still run; one log line with the counts; shutdown waits for a running pass). Constants: `PENDING_SIGN_UP_TTL_MS` (`sign-up-rules.ts`), `RATE_LIMIT_LONGEST_WINDOW_MS` (24 h, a test keeps every rule within it), `SESSION_MAX_AGE_MS` reused.
- Pending sign-ups go when unverified and past `app_user.pending_expires_at` (new nullable column, same migration; null, every existing user, is never deleted). Both columns sit on the row the single `DELETE` locks, and Postgres re-checks them after the lock wait, so a re-submit or a verification racing the cleanup keeps the account.
- Review fixes: `AuthRateLimiter` throws before counting under a rule longer than `RATE_LIMIT_LONGEST_WINDOW_MS`; a failed step also goes to Sentry (label and error kind only); shutdown skips a running pass's remaining steps; the nightly backup leaves out the data of `auth_rate_limit`, `auth_token` and `auth_username_hold`.
- Not cleaned: a revoked session (epoch raised) stays until its own expiry (at most 30 days, it cannot renew); password reset (1e) deletes sessions itself.
- Next: 1e, sign-up and email verification with a console `EmailSender` (Brevo later), then 1f, the web side. For 1e:
  - Every submit and resend sets `pending_expires_at` = now + `PENDING_SIGN_UP_TTL_MS` in the UPDATE that re-arms the account; verification clears it.
  - Availability and the 409 read only verified users and live holds; sign-up replaces a stale unverified row in its own transaction, so the cleanup's timing never tells whether an email or username exists.
  - Verification locks the `app_user` row before consuming the token, in the same order as the cleanup's cascade, so the two cannot deadlock.
  - Deferred: a CHECK on token lifetime (`expires_at > created_at`) and UNIQUE(`user_id`, `purpose`).
- Follow-up idea: send a failed cleanup step to Sentry (today a warning only).
