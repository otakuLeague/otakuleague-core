# OTA-139: accounts, slice 1d (auth cleanup timer)

- New tables (migration `20261117120000_auth_token_username_hold`, additive): `auth_token` (`token_hash` 32-byte PK, `purpose` enum `auth_token_purpose`, `user_id` FK ON DELETE CASCADE, `binding_hash`, `created_at`, `expires_at`, `used_at`) and `auth_username_hold` (`username_key` PK, `expires_at`). SQL-only CHECKs: 32-byte `token_hash` and `binding_hash`, a binding on `EMAIL_VERIFICATION` only. Nothing writes them yet: slice 1e does.
- `AuthCleanupService` (five `deleteMany`, `now` from `Clock`, each at the cutoff its rule already treats as ended) and `AuthCleanupScheduler` (a minute after boot, then every 24 h; a failing step is one warning and one Sentry warning with its label and error kind only, and the others still run; one log line with the counts; shutdown skips the remaining steps and waits for the pass). Constants: `PENDING_SIGN_UP_TTL_MS` (`sign-up-rules.ts`), `RATE_LIMIT_LONGEST_WINDOW_MS` (24 h; `AuthRateLimiter.check` refuses a longer rule before counting any key), `SESSION_MAX_AGE_MS` reused.
- Pending sign-ups go when unverified and past `app_user.pending_expires_at` (new nullable column, same migration; null, every existing user, is never deleted). Both columns sit on the row the single `DELETE` locks, and Postgres re-checks them after the lock wait, so a re-submit or a verification racing the cleanup keeps the account (an integration test holds the row lock to prove it).
- The nightly backup leaves out the data of `auth_rate_limit`, `auth_token` and `auth_username_hold` (`docs/deploy.md` lists what a restore loses); never-verified users and expired sessions stay in it.
- Dev database migrated at the earlier WIP commit of this branch (before `pending_expires_at` joined the migration): run `pnpm db:reset`, then `pnpm db:migrate`.
- Not cleaned: a revoked session (epoch raised) stays until its own expiry (at most 30 days, it cannot renew); password reset (1e) deletes sessions itself.
- Next: 1e, sign-up and email verification with a console `EmailSender` (Brevo later), then 1f, the web side. For 1e:
  - Every submit and resend sets `pending_expires_at` = now + `PENDING_SIGN_UP_TTL_MS` in the UPDATE that re-arms the account; verification clears it.
  - Availability and the 409 read only verified users and live holds; sign-up replaces a stale unverified row in its own transaction, so the cleanup's timing never tells whether an email or username exists.
  - Verification locks the `app_user` row before consuming the token, in the same order as the cleanup's cascade, so the two cannot deadlock.
  - Deferred: a CHECK on token lifetime (`expires_at > created_at`) and UNIQUE(`user_id`, `purpose`).
