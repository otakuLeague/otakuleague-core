# OTA-139: accounts slice 1c-i, sign-in rate limits and credential rules (2026-11-15)
## What changed
- Table `auth_rate_limit` (`key` 32-byte HMAC, `window_start`, `count`), migration `20261115140850_auth_rate_limit` with CHECKs (key length 32, count >= 1).
- `AuthRateLimiter` (`apps/api/src/auth/auth-rate-limiter.ts`): one atomic upsert per key, window reset in the same statement, `check(hits)` stops at the first refusal. Registered in `AuthModule`, no caller yet.
- Pure `auth-rate-limit-rules.ts` (`SIGN_IN_LIMITS` 30/IP and 5/(identifier, IP) per 15 min, 30/identifier per hour; `rateLimitKey`; `decide`) and `credential-rules.ts` (NFC password, length in code points, normalised identifier, `identifierKind`, bounds 8/128/254). `PasswordHasher` normalises through `normalisePassword`.
- `AUTH_HMAC_KEY` (env validation, `AuthSecrets`/`EnvironmentAuthSecrets`), `.env.example`, `docs/deploy.md`, screenshots CI fake value, `hmac` in the redaction pattern.
- Error codes `INVALID_CREDENTIALS`, `TOO_MANY_REQUESTS` in shared-types.
- ADR 0015: "Built so far"; dates edited in place (runtime proof 2026-11-23, Google cutoff 2026-11-27, Farouk 2026-11-15); the two accepted rate-limit trade-offs.
## Decisions
- `.env.example` says `openssl rand -hex 32`, not `-base64 32`: the reused validator refuses `+`, `/` and `=`.
- `check` takes only branded `RateLimitHits` from `signInHits` (fixed order ip, (identifier, IP), identifier); IP parts are `ClientIpKey`, which `clientIpKey` refuses to build for the shared `unknown`/`preview` buckets.
- Accepted trade-offs, recorded in ADR 0015: fixed windows allow a 2 x limit - 1 burst across a boundary; the identifier ceiling is per spelling (up to 2x per account) so a caller cannot link a username to an email.
- `AUTH_HMAC_KEY` is used as its UTF-8 bytes, held as a `KeyObject` (immutable, prints nothing). Also refused when equal to `INTERNAL_API_KEY_PREVIEW`.
- HMAC input is `JSON.stringify(['auth-rate-limit', route, scope, ...parts])`: unambiguous and domain-separated from any later use of the key.
- Window start comes back as epoch ms: the pg adapter reads a timestamptz without its offset, so a non-UTC session time zone shifted windows by hours (seen in a local run with `timezone = 'Asia/Tokyo'`). Other raw timestamptz reads (`SessionService`) have the same latent issue (production Postgres runs in UTC): OTA-200.
