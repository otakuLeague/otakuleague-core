# OTA-220: Jikan fill-in logs only "TypeError" (branch `fix/OTA-220-jikan-fallback`)

- Changed: `requestJson` (`apps/api/src/anime/sources/source-http.ts`, private `fetchFailureReason`) logs why a fetch or body read failed, e.g. `jikan unavailable: TypeError (ECONNREFUSED)`: the cause's code, else its class; for an AggregateError each address's code (at most 4, deduped); never a message, which can quote the URL. No API, variable, dependency or error-code change.
- Root cause in code: fetch reports every network failure as `TypeError: fetch failed` with the real error in `cause`, and we logged `error.name` only. Config ruled out: on the compiled build an empty `JIKAN_API_URL` still gives `https://api.jikan.moe/v4`, and that host was resolved in production.
- Likely network cause (unconfirmed): the ~250 ms after DNS is Node's happy-eyeballs attempt timeout. A local repro (A record unanswered, AAAA unroutable) gives `TypeError: fetch failed` after 280 ms, cause AggregateError [ETIMEDOUT, EAFNOSUPPORT], while AAAA first gives a TimeoutError at the full timeout. So in production the IPv4 handshake to Jikan goes unanswered and there is no IPv6 egress. A TLS failure is the other candidate.
- Tests: `source-http.spec.ts` "requestJson network failures" (fake fetch: code-only cause, Error cause by code, Error cause by class, AggregateError, unsafe code left out; real ERR_INVALID_URL and loopback ECONNREFUSED), written first and failing on the old code.
- Open: after deploy, read the next `jikan unavailable: TypeError (...)`. If it shows `ETIMEDOUT, ENETUNREACH`, try IPv4 alone in `railway ssh` (`node --no-network-family-autoselection --dns-result-order=ipv4first`). If that answers, set `NODE_OPTIONS` to those two flags; otherwise Jikan drops Railway egress, which no code fixes. A TLS code (`CERT_*`, `UNABLE_TO_*`) means waiting or reporting upstream; never disable verification.
