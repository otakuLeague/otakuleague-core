# OTA-223: throttle GET /auth/verify in the proxy

- Branch `fix/OTA-223-verify-throttle`. Web only: no API change, variable, dependency or error code. Closes the ADR 0015 Addendum 1f-vi "Too simple?" gap (amended there): past the cap a network's openings cost the API nothing. It does not close the OTA-139 Minor: a cross-site forced GET still spends the victim network's 10 (web count and API count alike).
- Guard `createVerifyLinkThrottleGuard` (`apps/web/src/auth/verify-link-throttle-guard.ts`): `pass` or `answer`, like the action guard. Counts only what `verifyEmailLink` would send to the API: pathname exactly `EMAIL_VERIFICATION_LINK.path`, `linkRequestKindOf` `navigate` (a GET only), `emailLinkTokenFrom` defined, a known client. Over the cap: `seeOther(EMAIL_LINK_LANDINGS.tryAgain)` (bodiless 303, `no-store`, no Referer, constant `Location`). No I/O, no log.
- Counter `VERIFY_LINK_THROTTLE_CONFIG`: 10 per IPv4 or /64 per 15 min, 10,000 keys, no /48 tier, separate from the action counters; same per-instance keyer (one `randomBytes`). `throttleClientOf` (was the private `actionClientOf`) is exported so both guards read the client the same way.
- Proxy order: action guard, link guard, slug door. Matcher gains the literal `/auth/verify` (landings under it stay out; a test pins it to the shared constant).
- Unknown client (no or malformed `x-forwarded-for` on Vercel, an https host off Vercel) passes uncounted: the handler's `credentialCall` then refuses with 0 calls (`client_ip_unknown` reported there, or a configuration throw).
- Tests: matcher rows and pin; guard cap, window edge, refusals uncounted, per /64 with no /48, every uncounted kind (prefetch, HEAD, POST, image, frame, fetch, bad tokens, other paths, unknown client), 10 prefetches then a click, mail app without Fetch Metadata, one machine, memory and privacy; through `proxy()`: over-cap answer shape with 0 fetches, and budget isolation both ways with action POSTs.
- Path (review W1): compared percent-decoded with one trailing `/` trimmed, since Next tries the proxy matcher on the raw and the decoded path. On `next start` (16.4.6, fake API) `/auth/%76erify`, `/%61uth/verify` and `/auth%2Fverify` answered 404 and `/auth/verify/` a 308 before the proxy, so none reached the handler there; counting them is the safe direction.
- The guard over-counts (safe direction) an opening the handler then ends before the API call (a configuration throw, a preview, a decoded spelling that answers 404). No /48 tier at the web tier: a network rotating /64s gets 10 per /64.
- Decision (autopilot, in the PR): the over-cap answer is `seeOtherFromProxy` (`see-other.ts`), the same bodiless 303 with an absolute `Location` under `WEB_PUBLIC_URL`, never the request's origin: Next's proxy adapter parses `Location` with `new NextURL()` (`server/web/adapter.js`), so the relative one was a 500. Without a valid `WEB_PUBLIC_URL` the guard passes uncounted. Checked on `next start` (16.4.6, fake API): openings 1 to 10 reached the API, 11 and 12 got `303 Location: /auth/verify/try-again` (relativized by the adapter), `no-store`, no cookie, 0 more calls.
- Open: per instance only, so the web cap is 10 × instances; the API's Postgres counter stays the real bound. On a preview the guard still counts, so past 10 an opening lands on `try-again` instead of `/auth`: harmless, previews make no calls.
