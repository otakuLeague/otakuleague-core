# 0008: Franchise and season chain
Status: accepted (2026-10-16, owner decisions in OTA-95)

## Context
OTA-95. The season selector (OTA-97) needs an ordered list (Season 1, 2, 3...) and the Related tab (OTA-112) needs the other entries grouped by type. AniList only gives a graph: each anime lists its direct neighbours with a relation type. A naive walk breaks on split cours (Attack on Titan Final Season parts), on movies inside a chain (Demon Slayer Mugen Train), on alternative versions (Fullmetal Alchemist 2003 vs Brotherhood) and on non-linear or very long franchises (Monogatari, Fate, Gintama).

Constraints: ADR 0006 (AniList primary, on-demand import, 30-day purge of what nobody opens, one AniList limiter of 30 requests/min per process, adult entries never stored or shown), ADR 0007 (identity and slugs keyed on the AniList id; slugs claimed only at import; removed identities never shown).

Facts checked against AniList (docs repo and one probe request, 2026-10-16):
- `MediaRelation`, `relationType(version: 2)`: ADAPTATION, PREQUEL ("Released before the relation"), SEQUEL ("Released after the relation"), PARENT, SIDE_STORY, CHARACTER, SUMMARY, ALTERNATIVE, SPIN_OFF, OTHER, SOURCE, COMPILATION, CONTAINS (COMPILATION and CONTAINS come from the docs only: no recorded edge has them). SEQUEL/PREQUEL describe release order, not "same story".
- `Page(perPage: 100)` answers `perPage: 50`: 50 is the maximum per request.
- Recorded walks (fixtures README): AoT's THE FINAL CHAPTERS are SPECIALs; AoT Season 1's PREQUEL is an OVA; Fate/Zero's SEQUEL/PREQUEL edges join three alternative routes; One Piece's SEQUEL/PREQUEL edge leads to an ONA (MONSTERS); Monogatari has an ONA season and nodes with several sequels; Demon Slayer's unaired sequels are movies with no date; Frieren has an unaired TV 3rd Season.

## Options
1. **Relations in the core snapshot** (`anime_source_snapshot`). Rejected: the core query has no relations, and a walked entry stored as an `Anime` with a thin snapshot would be served as a full page by `AnimeService.serve()` for up to 7 days.
2. **A stored franchise with a key** (the earliest main-line entry). Rejected: the key changes while a walk is partial or when AniList adds a prequel, and overrides keyed on it silently detach.
3. **One deeply nested GraphQL query per franchise.** Rejected: AniList's complexity limits are unverified and the answer grows with each level.
4. **MAL/Jikan relations.** Rejected: one primary source per field (ADR 0006).
5. **A table of walked nodes, keyed on the AniList id, filled by a small batched query, with the franchise computed at read time.** Chosen.

## Decision
1. **Walk data has its own table**, `anime_relation_node`: one row per walked AniList anime with its summary (titles, format, status, start date, cover) and all its edges, each with the target's summary. Adult entries and adult targets are dropped before storing. No synopsis, scores or tags. It never touches `anime` or the core query.
2. **Fetching**: `ANILIST_RELATIONS_QUERY`, one `Page(media(id_in))` request for 1 to 50 ids, `relationType(version: 2)` pinned; the walker splits a larger level over several requests, each waiting for its own free slot. A page AniList truncated (`hasNextPage`) or an answer with no Page fails like an HTTP error. An entry whose `isAdult` is not `false` is dropped. An id missing from an answer (unknown, adult, or nulled by a partial GraphQL error, which is accepted next to a usable Page) means "not now": it is backed off (item 11) and never treated as deleted. A walk request takes an AniList slot only when one is free right now (`maxQueueMs: 0`), so a page request waits at most one slot (2 s) behind a walk; on "queue full" the walker retries later. On a linear chain a level is one node, so a walk costs about one request per entry (AoT: 8 requests for 9 entries).
3. **The walk** runs in the background, started by the franchise endpoint when rows are missing or stale, never during a page request: one walker per process, one walk at a time, skipping nodes it holds fresh (known limit: no per-franchise single-flight; add it if overlapping walks ever matter), a queue of at most 100 start ids (a request for an id already queued or being walked is ignored; beyond 100 it is dropped and logged), and a stop flag set at module destroy, before Prisma disconnects, so shutdown waits only for the request in flight. A walk ends `complete`, `missing` (an id AniList left out; backed off, item 11), `truncated` (node cap) or `stopped` (AniList off or cooling down, or shutdown); fetched batches are stored as they arrive, each row upserted on its own in id order (no transaction, so two processes cannot deadlock). It follows SEQUEL and PREQUEL edges to non-adult anime, through any format, up to a node cap (60, an estimate; the longest recorded walk has 14 entries). Between a `BOUNDARY` entry and its prequels no edge is followed, from either side (item 8). The rule is one pure function, `isFollowedEdge`, applied by `traverseFranchise`, which the walker and the read path both go through (item 4). Known limit: AniList edges are assumed symmetric (all 106 recorded SEQUEL/PREQUEL edges are); an edge listed on one side only is followed only from that side.
4. **The franchise is computed at read time**, never stored, no franchise key: one traversal function, `traverseFranchise` (`franchise-graph.ts`), shared by the walker and the read path so both reach the same entries by construction. It goes level by level over `isFollowedEdge` with a sorted frontier and the node cap, through a loader: the walker's reuses fresh rows and asks AniList for the others, the read path's reads stored rows. `buildFranchise` (`franchise-view.ts`, pure) turns the result into the view. State: `complete`; `walking` when an entry has no row yet (what is known is returned); `truncated` when the node cap cut it. The read path passes every BOUNDARY id in the database, and removed identities among the entries and their edge targets. Known limit: the loaders differ on one point (a stale row AniList now omits is walked through by the read path, not by the walker). An id AniList leaves out is backed off (item 11): while it is, it neither keeps the franchise `walking` nor queues a walk.
5. **Main line**: component members whose format is TV, TV_SHORT or ONA (owner decision: ONA counts) and whose status is not CANCELLED, plus `SEASON` overrides, minus `RELATED` overrides, minus removed identities, ordered by start date (year, month, day, then AniList id); an entry with no date goes last. Unaired entries are included with `status: NOT_YET_RELEASED`.
6. **Labels** (owner decision, OTA-95 PR4): an override label wins and takes no position. Every other entry is labelled from what its title adds to the franchise's base title, the first main-line entry's without an override label (English titles when both have one and they share the base, else romaji; the base is removed at a word boundary, then the separators after it): "Demon Slayer: Kimetsu no Yaiba Entertainment District Arc" gives "Entertainment District Arc", "Attack on Titan Final Season" gives "Final Season", "Gintama.: Slip Arc" gives "Slip Arc". Nothing left (the first entry) gives "Season <position>" by air order. A remainder that only names a season number ("Season 3", "3rd Season", "Third Season", "3", or a Roman numeral alone such as "III", unambiguous after the base title) gives "Season <that number>", so Gintama Season 3 stays Season 3 even though it is the fourth entry. A title that does not start with the base title stays whole (Monogatari's entries). Two computed labels that clash show their titles instead, then the start year, then the AniList id.
7. **Related**: members that are not seasons, plus every target of a non-followed edge of a member, deduplicated, minus members of the main line, adult entries and removed identities. Groups: `source` (any manga), `spin_off` (SPIN_OFF, ALTERNATIVE, CHARACTER, OTHER), otherwise by format (`movie`, `ova`, `special`, `ona`, `tv`, `music`, and `other` for an unknown format, such as an announced entry); a target reached by several edges takes the first of source, spin-off, format; members keep their format group. Each group is sorted by air date. OTA-112 may regroup: it is one pure function.
8. **Overrides**: `anime_franchise_override`, one row per AniList id: `role` (`SEASON` forces into the main line, `RELATED` forces out, `BOUNDARY` means "the franchise starts here" (owner decision): no edge between this entry and its prequels is followed, in either direction, while its sequels stay linked, so the franchise is the same whichever entry it is computed from; a `BOUNDARY` entry is a season or not by its format like any other), optional `label` (1 to 60 characters, CHECK), required `note`. No reorder override: air order is right when dates are right, and wrong dates are fixed upstream at AniList. An override on an id outside the component does nothing. Editing path: a reviewed data migration (`migrate dev --create-only`, then SQL), so every environment gets it; integration tests start from empty tables and insert the overrides they need. Later override migrations use `INSERT ... ON CONFLICT ("anilist_id") DO UPDATE SET "role" = EXCLUDED."role", "label" = EXCLUDED."label", "note" = EXCLUDED."note"` (never touching `created_at`), so a migration that copies an urgent psql fix into the repository does not fail on the row production already has; removing an override is an explicit `DELETE` in a migration. The database rejects a label over 60 characters or of only spaces (tightened by migration `franchise_override_label_trim`), a row with neither role nor label, and a blank note. "No code change" means no code, not no review. Overrides only include, exclude, set boundaries and rename. Shipped with the walker migration (owner decisions): One Piece's MONSTERS ONA (167404) `RELATED`; Attack on Titan THE FINAL CHAPTERS Special 1 and 2 (146984, 162314) `SEASON`, labelled "The Final Chapters Part 1" / "Part 2"; Fate/stay night 2006 (356), Unlimited Blade Works TV (19603) and movie (6922), Heaven's Feel I (20791) `BOUNDARY`, which leaves Fate/Zero, UBW, Heaven's Feel and the 2006 series as four franchises.
9. **Endpoint**: `GET /anime/slugs/:slug/franchise` (three segments, no clash with the two-segment routes), `AnimeFranchise` in shared-types: `state` (`complete`, `walking`: entries still coming, ask again later; `partial`: AniList just left an entry out, the list may be incomplete for a while; `truncated`: the node cap cut it; `unavailable`: AniList switched off, empty lists, nothing deleted), `mainLine` (label, slug, isCurrent and the entry summary), `related` (groups of at most 50 with their total). Any slug of the identity answers, with no redirect; a removed identity or an unknown slug is a 404. It reads stored rows only, never a source, and queues a walk when the start has no row, a row is stale, or an id is missing and not backed off. Entries carry `slug: string | null` (null until the anime is imported; the web app then links the id route, OTA-97; always null for manga). The main line is bounded by the node cap; Related by the node cap times the edges per node, deduplicated, so each group returns at most 50 entries plus its total: the documented exception to "every list endpoint is paginated".
10. **Expiry**: serving a franchise bumps `last_used_at` (deliberately not `last_viewed_at`: used by a franchise view, not a page view) on every row it shows, Related neighbours included, at most once an hour; rows unused for 30 days are purged with the anime purge; stale rows refresh on the same TTL as anime (7 days, 1 day while airing).
11. **Backoff** (`SourceBackoff`, owner decisions): one mechanism for every answer that is neither found nor a clean "not found": an anime AniList answers without a usable `isAdult`, and an id AniList leaves out of a relations answer. Graduated: each repeated bad answer waits longer, 1 hour, 6 hours, 1 day, then 7 days; a good answer resets it, and an expired entry keeps its step so the next bad answer waits longer. While any missing id of a franchise is on an early step (before 7 days), the franchise is `partial`, not `complete`, so the page can say the list may be incomplete; one truncated answer during a short incident hides a season for about an hour: the first view after it answers `walking` and queues a walk, and the next one shows the season again. An id left out at every retry reaches the week-long step, and the franchise is `complete` without it. Keys are per kind (`anime:` and `relations:`), so an id left out of a relations answer never blocks importing that anime and the reverse. A backed-off anime is not even chosen for a refresh; a backed-off relations id neither keeps a franchise `walking` nor queues a walk, even when its row is stale or it is the start. In memory and per process: a restart starts every entry at the first step again, which costs up to 4 requests and about 31 hours of `partial` for an id AniList never returns (accepted; persist the step if it shows in practice; a shared table if several API instances ever run).

## Consequences
- Walk data is AniList data for entries nobody opened, bounded by the node cap per franchise viewed in the last 30 days. Legally the same position as the rest of the cache, pending OTA-127.
- `anime_relation_node` reuses the `anime_format` and `anime_status` enums: renaming or removing a value must migrate this table too; as it is a cache, that migration may simply truncate it.
- The daily purges run fire-and-forget: one running during shutdown may log a warning.
- Every walk request goes through the per-process limiter: N API instances mean N x 30 requests/min (already on OTA-85).
- A failed walk request (HTTP failure, no Page, truncated page) starts the AniList cool-down (5 s), which also pauses page imports, as background refreshes already do. A 429 shows up as "queue full" to the walker, because the pause holds the next slot.
- Targets (not measured): endpoint p95 under 50 ms from the database; a first complete walk takes about levels x 2 s.
- Fate-like franchises need `BOUNDARY` or `RELATED` overrides; this is expected, not a bug. Overrides are per entry, not per edge: a boundary cuts all of an entry's prequel links, which fits every recorded case.
- The review proposed `BOUNDARY` as "not walked through unless the walk starts there". Rejected while building the walker: the component then depends on the start (from UBW 2nd Season, UBW would be cut off and UBW 2nd Season left alone).
- Scope (owner decision: no split, OTA-95 is size L): 4 PRs, about 1,250 lines (estimate): fetching (#25), storage, walker and overrides table, pure computation, endpoint. Each says "Part of OTA-95", the last one "Closes OTA-95".

## Owner decisions (2026-10-16)
1. ONA counts as a season; exceptions are overrides (One Piece's MONSTERS is `RELATED`).
2. No ticket split: OTA-95 is size L, delivered in 4 PRs.
3. No reorder override, slug route only, the Related grouping above.
4. The core mapper no longer treats a missing `isAdult` as safe, like the relations mapper. It refuses such an answer as unusable (the source counts as unavailable: nothing shown, stored or removed) rather than flagging it adult, because an adult flag deletes the anime and blocks it for good (ADR 0007), which a transient glitch must not do. Only `isAdult: true` removes an anime.
