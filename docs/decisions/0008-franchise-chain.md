# 0008: Franchise and season chain
Status: proposed (open questions at the end; accepted once the owner answers them)

## Context
OTA-95. The season selector (OTA-97) needs an ordered list (Season 1, 2, 3...) and the Related tab (OTA-112) needs the other entries grouped by type. AniList only gives a graph: each anime lists its direct neighbours with a relation type. A naive walk breaks on split cours (Attack on Titan Final Season parts), on movies inside a chain (Demon Slayer Mugen Train), on alternative versions (Fullmetal Alchemist 2003 vs Brotherhood) and on non-linear or very long franchises (Monogatari, Fate, Gintama).

Constraints: ADR 0006 (AniList primary, on-demand import, 30-day purge of what nobody opens, one AniList limiter of 30 requests/min per process, adult entries never stored or shown), ADR 0007 (identity and slugs keyed on the AniList id; slugs claimed only at import; removed identities never shown).

Facts checked against AniList (docs repo and one probe request, 2026-10-16):
- `MediaRelation`, `relationType(version: 2)`: ADAPTATION, PREQUEL ("Released before the relation"), SEQUEL ("Released after the relation"), PARENT, SIDE_STORY, CHARACTER, SUMMARY, ALTERNATIVE, SPIN_OFF, OTHER, SOURCE, COMPILATION, CONTAINS (COMPILATION and CONTAINS come from the docs only: no recorded edge has them). SEQUEL/PREQUEL describe release order, not "same story".
- `Page(perPage: 100)` answers `perPage: 50`: 50 is the maximum per request.
- Recorded walks (fixtures README): AoT's THE FINAL CHAPTERS are SPECIALs; AoT Season 1's PREQUEL is an OVA; Fate/Zero's SEQUEL/PREQUEL edges join three alternative routes; One Piece's SEQUEL/PREQUEL edge leads to an ONA (MONSTERS); Monogatari has an ONA season and nodes with several sequels; Demon Slayer's unaired sequels are movies with no date; Frieren has an unaired TV 3rd Season.

## Options
1. **Relations in the core snapshot** (`anime_source_snapshot`). Rejected: the core query has no relations, and a walked entry stored as an `Anime` with a thin snapshot would be served as a full page by `AnimeService.serve()` for up to 7 days.
2. **A stored franchise with a key** (the earliest main-line entry). Rejected: the key changes while a walk is partial or when AniList adds a prequel, and overrides keyed on it silently detach.
3. **One deeply nested GraphQL query per franchise.** Rejected: AniList's complexity limits are unverified and the answer grows with each level.
4. **MAL/Jikan relations.** Rejected: one primary source per field (ADR 0006).
5. **A table of walked nodes, keyed on the AniList id, filled by a small batched query, with the franchise computed at read time.** Chosen.

## Decision
1. **Walk data has its own table**, `anime_relation_node`: one row per walked AniList anime with its summary (titles, format, status, start date, cover) and all its edges, each with the target's summary. Adult entries and adult targets are dropped before storing. No synopsis, scores or tags. It never touches `anime` or the core query.
2. **Fetching**: `ANILIST_RELATIONS_QUERY`, one `Page(media(id_in))` request for 1 to 50 ids, `relationType(version: 2)` pinned; the walker splits a larger level over several requests, each waiting for its own free slot. A page AniList truncated (`hasNextPage`) or an answer with no Page fails like an HTTP error. An entry whose `isAdult` is not `false` is dropped. An id missing from an answer (unknown, adult, or nulled by a partial GraphQL error, which is accepted next to a usable Page) means "not now": the walker retries it on the next refresh and never treats it as deleted. A walk request takes an AniList slot only when one is free right now (`maxQueueMs: 0`), so a page request waits at most one slot (2 s) behind a walk; on "queue full" the walker retries later. On a linear chain a level is one node, so a walk costs about one request per entry (AoT: 8 requests for 9 entries).
3. **The walk** runs in the background after an anime is served, never during a page request: one walker per process, one walk at a time, skipping nodes it holds fresh (known limit: no per-franchise single-flight; add it if overlapping walks ever matter), with an abort flag checked between levels so shutdown and tests do not wait for it. It follows SEQUEL and PREQUEL edges to non-adult anime, through any format, up to a node cap (60, an estimate to confirm on the fixtures).
4. **The franchise is computed at read time** from the stored rows, starting from the requested anime: the connected component over SEQUEL/PREQUEL, never stored, no franchise key.
5. **Main line**: component members whose format is TV, TV_SHORT or ONA and whose status is not CANCELLED (open question 1), minus removed identities, ordered by start date (year, month, day, then AniList id); an entry with no date goes last. Unaired entries are included with `status: NOT_YET_RELEASED`.
6. **Labels**: parse the English title, else the romaji one, for "Season N", "Nth Season", "First...Tenth Season", "Final Season" and "Part N" / "Cour N" (no Roman numerals: too ambiguous). If no main-line title has a marker, label by position ("Season 1", "Season 2"...). Otherwise a parsed title gives "Season N", "Final Season", "Season N Part P"; the first entry without a marker is "Season 1"; any other keeps its title. A label used twice gets " (year)", or " (AniList id)" without a year.
7. **Related**: the non-followed edges of every component member plus component members that are not seasons, deduplicated, minus main-line members, adult entries and removed identities. Groups: `source` (any manga), `spin_off` (SPIN_OFF, ALTERNATIVE, CHARACTER, OTHER), otherwise by format (`movie`, `ova`, `special`, `ona`, `tv`, `music`). OTA-112 may regroup: it is one pure function.
8. **Overrides**: `anime_franchise_override`, one row per AniList id: `role` (`SEASON` forces into the main line, `RELATED` forces out, `BOUNDARY` is not walked through and cuts a bad bridge such as Fate's alternative routes), optional `label` (1 to 60 characters, CHECK), required `note`. No reorder override: air order is right when dates are right, and wrong dates are fixed upstream at AniList. An override on an id outside the component does nothing. Editing path: a reviewed data migration (`migrate dev --create-only`, then INSERTs), so every environment and the tests get it; an urgent production fix goes through psql and is copied into a migration in the next PR. "No code change" means no code, not no review.
9. **Endpoint**: `GET /anime/slugs/:slug/franchise` (three segments, no clash with the two-segment id route). Any slug of the identity answers, with no redirect. The answer carries `walk.state`: `complete`, `walking` (data still coming; the client may refetch), `truncated` (node cap reached) or `unavailable` (AniList switched off: empty lists, nothing deleted). Entries carry `slug: string | null` (null until the anime is imported; the web app then links the id route, OTA-97). The main line is bounded by the node cap; Related is bounded by the node cap times the edges per node, deduplicated (one One Piece node has 65 edges), so each Related group returns at most 50 entries plus its total count. Together, the documented exception to "every list endpoint is paginated".
10. **Expiry**: serving a franchise bumps `last_used_at` on its rows at most once an hour; rows unused for 30 days are purged with the anime purge; stale rows refresh on the same TTL as anime (7 days, 1 day while airing).

## Consequences
- Walk data is AniList data for entries nobody opened, bounded by the node cap per franchise viewed in the last 30 days. Legally the same position as the rest of the cache, pending OTA-127.
- Every walk request goes through the per-process limiter: N API instances mean N x 30 requests/min (already on OTA-85).
- A failed walk request (HTTP failure, no Page, truncated page) starts the AniList cool-down (5 s), which also pauses page imports, as background refreshes already do. A 429 shows up as "queue full" to the walker, because the pause holds the next slot.
- Targets (not measured): endpoint p95 under 50 ms from the database; a first complete walk takes about levels x 2 s.
- Fate-like franchises need `BOUNDARY` or `RELATED` overrides; this is expected, not a bug.
- Scope: about 1,250 lines over 4 PRs (estimate): fetching (this PR), storage and walker, pure computation, endpoint and overrides. The owner decides whether OTA-95 is split.

2. **Ticket size**: keep OTA-95 as one ticket with 4 PRs, or split it (walk and storage / computation and endpoint)?
3. **Product choices** taken from the review: no reorder override, slug route only, the Related grouping above.
